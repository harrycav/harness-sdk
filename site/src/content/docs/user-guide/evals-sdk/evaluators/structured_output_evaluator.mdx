## Overview

The `StructuredOutput` evaluator scores an agent's structured output against ground truth **field by field**, rather than comparing whole objects. Where [`Equals`](deterministic_evaluators.md) returns only `0.0` or `1.0`, `StructuredOutput` tells you *which field to fix*: an extraction that gets nine of ten fields right is no longer indistinguishable from one that gets none right.

It is deterministic and offline — no LLM judge, no credentials, no per-call cost. Configuration is derived from the Pydantic model your agent already supplies as `structured_output_model`, so no schema or annotation work is required, and every inferred decision is inspectable via `explain()`. A complete example can be found [here](https://github.com/strands-agents/harness-sdk/blob/main/site/docs/examples/evals-sdk/structured_output_evaluator.py).

This evaluator requires the optional `stickler` extra:

```bash
pip install "strands-agents-evals[stickler]"
```

Without it, constructing the evaluator raises an `ImportError` naming the command above.

## Key Features

- **Field-Level Scoring**: Per-field scores and per-field metrics, not a single pass/fail
- **Order-Independent List Matching**: A reordered but identical list scores `1.0`, not `0.0`
- **Zero Configuration**: Comparators and thresholds are inferred from the Pydantic model
- **Deterministic and Offline**: Pure computation — no LLM judge, no credentials, no per-call cost
- **Inspectable**: `explain()` reports the comparator chosen for each field and why
- **Dataset Metrics**: Confusion-matrix counts per dotted field path across the whole run

## When to Use

Use the `StructuredOutput` evaluator when you need to:

- Evaluate extraction or structured-output tasks where partial correctness matters
- Identify *which* field regressed, not just that a case failed
- Score outputs containing lists of nested objects, where ordering is not meaningful
- Run evaluations in CI/CD without model credentials or inference cost
- Track per-field accuracy across a dataset to target the worst-performing field

Prefer [`Equals`](deterministic_evaluators.md) when the output is a scalar and only exact equality matters.

## Parameters

### `model_cls` (optional)
- **Type**: `type[BaseModel] | None`
- **Default**: `None`
- **Description**: The Pydantic model to score against — the same model the agent emits as `structured_output_model`. When supplied, every case is coerced to it and non-validating input raises, which suits a single-schema suite. When omitted, the class is inferred per case, which suits a suite that mixes output types — `metrics()` is keyed by model class either way.

### `match_threshold` (optional)
- **Type**: `float`
- **Default**: `0.7`
- **Description**: Similarity at or above which an object counts as a match. It sets the bar for per-element matching of `list[Model]` fields, for single nested `BaseModel` fields, and for `dict` fields, and it is what the weighted score is compared against — so it drives both halves of the `test_pass` rule (see [Scoring System](#scoring-system)). Scalar field thresholds are inferred from type and field name and are unaffected.

### `weight_hints` (optional)
- **Type**: `bool`
- **Default**: `False`
- **Description**: Whether to infer per-field weights from the schema. Off by default so weights stay uniform and metrics are not skewed by guessed business criticality.

### `name` (optional)
- **Type**: `str | None`
- **Default**: `None`
- **Description**: Display name, forwarded to the base `Evaluator`.

## Basic Usage

```python
from pydantic import BaseModel
from strands import Agent
from strands_evals import Case, Experiment
from strands_evals.evaluators import StructuredOutput


class LineItem(BaseModel):
    sku: str | None = None
    quantity: int | None = None


class Invoice(BaseModel):
    invoice_id: str
    vendor_name: str
    total_amount: float | None = None
    line_items: list[LineItem] = []


def extract(case: Case) -> Invoice:
    agent = Agent(callback_handler=None)
    result = agent(case.input, structured_output_model=Invoice)
    return result.structured_output


cases = [
    Case(
        name="invoice-0042",
        input="INVOICE #INV-2024-0042 — Acme Corporation — 2x WM-100, 5x UC-050 — Total: $124.93",
        expected_output=Invoice(
            invoice_id="INV-2024-0042",
            vendor_name="Acme Corporation",
            total_amount=124.93,
            line_items=[
                LineItem(sku="WM-100", quantity=2),
                LineItem(sku="UC-050", quantity=5),
            ],
        ),
    ),
]

# The same model the agent already emits as structured_output_model.
evaluator = StructuredOutput(Invoice)

experiment = Experiment(cases=cases, evaluators=[evaluator])
report = experiment.run_evaluations(extract)
report.run_display()
```

## Evaluation Output

The evaluator returns one `EvaluationOutput` per case with:

- **score**: Weighted mean of the per-field scores, between `0.0` and `1.0`
- **test_pass**: Boolean — requires the weighted score to clear `match_threshold` and, when anything was counted as findable, `recall` to clear it too. Per-field thresholds shape each field's score but are not themselves gates
- **reason**: The weakest imperfect fields, e.g. `"weakest fields: line_items=0.75"`, or `"all fields matched"`
- **label**: The model class name

`EvaluationOutput` carries only four scalar fields, so richer detail is read off the evaluator instead, reusing comparisons already performed:

```python
evaluator.per_case()   # per-document field scores, plus precision / recall / f1
evaluator.metrics()    # per-field confusion matrix, one rollup per model class
evaluator.explain()    # the comparator chosen per field, and why
evaluator.reset()      # drop accumulated results before reusing the instance
```

The instance accumulates: every case it scores is appended to a list that nothing in the harness clears. Reusing one evaluator across two experiments, or re-running the same experiment in one process, therefore doubles every count in `metrics()` and duplicates rows in `per_case()`. Call `reset()` between runs, or construct a fresh evaluator. The derived `cm_` ratios are unaffected by the duplication, so nothing looks wrong until you read a count.

`metrics()` returns one `ProcessEvaluation` per model class. Read its `field_metrics` attribute — the rollup is a Pydantic model, not a mapping, so `metrics()["Invoice"]["field_metrics"]` raises `TypeError`. `field_metrics` itself is a dict keyed by dotted path — `line_items.sku`, `line_items.quantity` — so a suite pinpoints the failing field across the dataset rather than merely flagging failure. Each entry carries the counts (`tp`/`tn`/`fn`/`fa`/`fd`, plus `fp` = `fa` + `fd`) and the derived metrics under `cm_`-prefixed keys: `cm_precision`, `cm_recall`, `cm_f1`, `cm_accuracy`. Most paths also carry a `mean_score`, but leaves under a `list[Model]` parent do not — `total_amount` has one, `line_items.sku` does not. Leaves under a single nested `BaseModel` do.

```python
metrics = evaluator.metrics()
metrics["Invoice"].field_metrics["total_amount"]["cm_precision"]
```

For `list[Model]` fields, a child path's counts only cover element pairs that scored at or above `match_threshold`. Below that the pair is treated as atomic and no field breakdown is emitted, so its children contribute nothing — a badly wrong element drops out of its children's counts entirely and can leave them reading perfect. Counts are also per matched element rather than per document, so `line_items.sku` may total more or fewer than the document count. Read a parent path such as `line_items` alongside its children. The other two nesting shapes behave differently again. Children of a single nested `BaseModel` are emitted whenever the parent is present on both sides, whatever it scored; if either side is missing the object, only the parent path is counted. That gives object-nested children the same hazard by a second route — across a dataset, documents that dropped the object contribute `fn` to the parent and nothing at all to the children, so a child can read `cm_recall` of `1.0` while the parent reads `0.667`. A `dict[str, Model]` field emits no child paths at all, even when its values match exactly — for a dict, the parent path is all you get.

:::caution[Do not positionally zip `per_case()` with `report.scores`]
`per_case()` is ordered by case completion, while `report.scores` is index-ordered, and failed evaluators add zero-score rows. Join on `case` instead — and `reset()` first if the instance has already been run, or each case name matches two rows.
:::

## Scoring System

The score is a **weighted mean of per-field scores**, ranging from `0.0` to `1.0`, where higher is better. Because it is computed rather than judged, the same inputs always produce the same score.

Ordering is the clearest difference from `Equals`. Given the invoice above:

| Scenario | `Equals` | `StructuredOutput` |
|---|---|---|
| List reordered, content identical | `0.0` | `1.0` |
| One quantity wrong, list reordered | `0.0` | `0.9375` |

In the second row, `reason` reads `"weakest fields: line_items=0.75"`, and `per_case()` returns `1.0` for `invoice_id`, `vendor_name`, and `total_amount` against `0.75` for `line_items` — the failing field is named, not inferred.

### Sparse schemas: read f1, not the score alone

A field absent on both sides is credited `1.0` — a value the model correctly left blank is a value it got right. On a mostly-empty schema those credits dominate: a ten-field model whose ground truth fills two fields still scores `0.80` against a prediction that returns **nothing**.

Raising `match_threshold` cannot fix this, because the score needed to pass tends toward `1.0` as the optional tail grows. This is why `test_pass` checks `recall` as well as the score: here the score of `0.80` clears the default `0.7`, but `recall` is `0.0`, so the case fails on recall alone. `per_case()` surfaces recall, precision, and f1 to show why.

Recall is not a complete safety net, though. It is `tp / (tp + fn)`, which counts values that were found but ignores values that were found *wrong* — those land in `fd`, in neither term. On the ten-field example above, a prediction returning one correct and one incorrect value scores `0.90` with **`recall` of `1.0`**, while `precision` is `0.5` and `f1` is `0.667`.

Two consequences worth internalising:

- On sparse schemas, report `f1` rather than the score or `recall` alone. `recall` can read `1.0` whenever at least one value was found and none was missed outright, however many came back wrong. With no `tp` at all it reads `0.0` instead, so a document that got everything wrong and one that got everything right report opposite extremes for the same reason: `fd` is in neither term.
- To tell these cases apart, read the counts in `metrics()`, not the scalars. Precision, recall, and f1 are all `0.0` for a document that returned nothing, one that returned every value wrong, and one that invented values against blank ground truth — the counts are the only thing that separates them: a miss is `fn`, a wrong value is `fd`, an invention is `fa`.

Two genuinely empty objects count as a match, not a failure. The recall gate is skipped whenever nothing was *counted* as findable (`tp + fn == 0`), which is what makes that case pass. Two other documents satisfy that same condition, because neither `fd` nor `fa` is counted as findable: one whose every expected value came back **wrong**, and one that **invented** values against blank ground truth. Both score `0.80` on the ten-field model and both pass `test_pass` on the score alone — the pure invention is the more alarming if you are using `test_pass` as a gate.

None of the scalars will tell you which of the three you have; precision, recall, and f1 are `0.0` for all of them. Read the counts in `metrics()`: `tn` only means genuinely empty, `fd` means wrong values, `fa` means invented ones.

## Best Practices

1. **Pass the model explicitly for single-schema suites**: `StructuredOutput(Invoice)` coerces every case and fails loudly on the wrong shape; omit it only when a suite genuinely mixes output types
2. **Read `metrics()` to choose what to fix**: the per-field confusion matrix reports how often each path is missed across the dataset — sort it yourself by `cm_recall`, or by `mean_score` if you skip the `list[Model]` children that lack one, and read parent paths beside nested ones
3. **Audit inferences before trusting them**: call `explain()` to confirm the comparator and threshold chosen for each field
4. **Report `f1` alongside the score on sparse schemas**: the score alone credits correct absence, and `recall` alone ignores values returned wrong
5. **Combine with LLM evaluators**: use `StructuredOutput` as a fast deterministic gate, then LLM-based evaluators for qualities that require judgement
